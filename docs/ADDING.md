# Как добавить своё

Все примеры идут от существующего: фреймворк `openvino`, модель `resnet50`. Ключи конфигов
описаны в [CONFIG.md](CONFIG.md). Новые файлы называйте так, как будете указывать в `--framework` и `--model`.

## Добавить модель

Самый простой случай: тот же фреймворк, другая модель.

1. Положите файлы модели в `models/<имя>/` (в git они не попадут, `.gitignore` это закрывает).
2. Скопируйте конфиг и поправьте:
   ```bash
   cp configs/models/resnet50.toml configs/models/<имя>.toml
   ```
   Измените `name`, `dir`, `files` (что копировать) и `entry` (какой файл передавать бенчмарку).
3. Соберите бандл. Фреймворк уже собран, поэтому `build` пропустится, а `package` и `verify` выполнятся заново:
   ```bash
   python3 build.py all --model <имя>
   ```
4. Заведите папку-заглушку для файлов модели: `touch models/<имя>/.gitkeep`.

Бандл получит имя `out/openvino-<имя>/`.

Если модель запускается другими аргументами (например, другой вход), а не только другим файлом, то
эти аргументы живут в `[run] command` конфига фреймворка. Тогда проще завести отдельный конфиг фреймворка
с тем же `[source]` (но не дублируйте исходники: `name` должен совпадать, и исходники скачаются один раз).

## Добавить фреймворк

Рекомендуемый порядок: идите **от нативной сборки на плате**. Всё, что в ней работало, переносится в конфиг.

1. **Скопируйте конфиг:** `cp configs/frameworks/openvino.toml configs/frameworks/<имя>.toml`
2. **`[source]` и `[[deps]]`:** репозиторий, тег (`git ls-remote --tags <repo>`), хеш коммита, нужны ли подмодули.
3. **`[[build]]`:** флаги `cmake` берите из нативной сборки (`CMakeCache.txt`, история команд). Зависимости,
   которые нужно устанавливать (`install_prefix`), - отдельными блоками перед фреймворком. Укажите `targets`,
   чтобы не собирать лишнее.
4. **`[[bundle]]`:** что скопировать в бандл: бенчмарк и все `.so`, которые он загружает
   (`readelf -d`, `ldd` на плате).
5. **`[run]`:** `bench`, `library_dirs`, `command` (из истории нативных запусков) и `metrics`: регулярки для
   чисел из вывода. Каждую регулярку проверьте на настоящем логе (команда в [CONFIG.md](CONFIG.md#run-как-запускать-на-плате-генерирует-runsh)).
6. **`[verify]`:** какие файлы должны быть RISC-V и какие строки должны остаться в бинарнике.
7. **Прогоните тесты** (они читают реальные конфиги, и ошибка в ключах всплывёт сразу):
   ```bash
   python3 -m unittest discover -s tests -v
   ```
   Часть тестов привязана к OpenVINO (например, проверка команд `cmake`), поэтому для нового фреймворка их
   стоит дополнить или скопировать с его параметрами.
8. **Собирайте этапами**, а не сразу `all`, и смотрите, что получается:
   ```bash
   python3 build.py doctor
   python3 build.py bootstrap      # если уже делали для другого фреймворка, пройдёт быстро
   python3 build.py fetch --framework <имя> --model <модель>
   python3 build.py patch ...      # если есть патчи
   python3 build.py build ...      # долго, запускайте в фоне
   python3 build.py package ...
   python3 build.py verify ...
   ```
   Для каждого этапа добавляйте `--framework <имя> --model <модель>`. Метки этапов хранятся отдельно
   для каждого фреймворка (`work/stamps/<имя>.<этап>`).

Исходники, сборка и результаты разных фреймворков лежат рядом в `work/` в папках с их именами, поэтому
имена в `[source]`, `[[deps]]` и `build_dir` не должны совпадать между фреймворками. Общий кросс-компилятор
(`work/toolchain`) ставится один раз.

## Добавить патч

Патч - это обычный `git diff`. Все патчи хранятся в `patches/<фреймворк>/` и перечисляются в `[[patches]]`.

1. Внесите правку в исходники в `work/src/<фреймворк>/` (или на плате).
2. Снимите патч **из того репозитория, где менялся файл**. Для подмодуля - из самого подмодуля:
   ```bash
   git -C work/src/<фреймворк> diff > patches/<фреймворк>/мой.patch
   git -C work/src/<фреймворк>/путь/к/подмодулю diff > patches/<фреймворк>/подмодуль.patch
   ```
3. Проверьте, что патч ложится на **чистые** исходники: `git -C <папка> stash && git -C <папка> apply --check <патч>`
   либо просто пересоберите исходники с нуля: `rm -rf work/src/<фреймворк> work/stamps/<фреймворк>.fetch`
   и выполните `fetch`, `patch`.
4. Впишите в конфиг фреймворка:
   ```toml
   [[patches]]
   file = "мой.patch"
   dir = "."                # или путь к подмодулю
   note = "что делает патч и откуда он взят"
   ```
5. Добавьте в `[verify]` строку, которая обязана остаться в бинарнике после патча.

Если патч снят с рабочей копии, у которой нет подтверждённого автора, честно напишите это в `note`
(как сделано для патчей OpenVINO): строка попадёт в `MANIFEST.txt`.

## Сменить плату

Правится только `configs/target.toml`: `arch`, `abi`, `tune`, `system_libs`, при необходимости кросс-GCC
(`cc`, `cxx`, `readelf`, `cross_debs`). Что откуда брать - [CONFIG.md](CONFIG.md#board-плата).
Если версия glibc на плате другая, подберите кросс-пакеты той же версии: библиотеки из sysroot
должны быть совместимы с системой платы.

После смены платы пересоберите всё заново: `rm -rf work/build work/install work/stamps` и `python3 build.py all`
(кросс-GCC и исходники при этом сохранятся).

## Поддержать другую систему сборки (не CMake)

`rvb/stages/build.py`: напишите функцию с той же сигнатурой, что `build_cmake(ctx, block)`, и добавьте
её в словарь `BUILD_SYSTEMS`. После этого в `[[build]]` можно писать `system = "<имя>"`. Дополнительные
ключи блока читайте через `block.get(...)`, а пути - через `ctx.sub(...)`, чтобы работали подстановки.

## Добавить этап

Создайте модуль в `rvb/stages/` по образцу любого из существующих (имена `NAME`, `HELP`, `SKIP_IF_DONE`
и функция `run(ctx)`) и впишите его в список `STAGES` в `rvb/stages/__init__.py` на нужное место.
Команды запускайте через `run(ctx, "<имя-лога>", [...])` из `rvb/runner.py`, и вывод сам попадёт в лог.
