# Справочник по конфигам

Три файла, каждый на своём уровне:

| Файл | Меняется, когда... |
|---|---|
| `configs/target.toml` | другая плата или другой кросс-компилятор |
| `configs/frameworks/<имя>.toml` | другой фреймворк или другая его версия |
| `configs/models/<имя>.toml` | другая модель |

Выбор при запуске: `python3 build.py all --framework openvino --model resnet50`
(значения - это имена файлов без `.toml`).

Если в конфиге нет обязательного ключа, скрипт сразу скажет, какого именно и в каком файле.

## Подстановки в путях и аргументах

В значениях из `[[build]]` и `[[bundle]]` можно писать:

| Запись | Значение |
|---|---|
| `{work}` | рабочая папка (`./work`, можно сменить переменной `RVB_WORK`) |
| `{src}` | `{work}/src`: исходники |
| `{build}` | `{work}/build`: каталоги сборки |
| `{install}` | `{work}/install`: результаты `cmake --install` |
| `{sysroot}` | `{work}/toolchain/root`: libc и заголовки для RISC-V |
| `{toolchain_file}` | сгенерированный CMake toolchain-файл |
| `{jobs}` | число параллельных задач |

Неизвестная подстановка (опечатка) - ошибка. В `[run] command` свои подстановки, см. ниже.

## `configs/target.toml`

### `[board]`: плата

| Ключ | Что это | Где взять |
|---|---|---|
| `name` | название для `MANIFEST.txt` | любое |
| `arch` | `-march`: набор команд процессора | на плате: `grep -m1 isa /proc/cpuinfo` показывает, что умеет процессор. Какой `-march` реально использовала нативная сборка: `grep -rh march --include=flags.make <каталог сборки>` (для Ninja смотрите `build.ninja`). Значение должно принимать и кросс-компилятор |
| `abi` | `-mabi`: как передаются аргументы функций | на плате: `c++ -Q --help=target \| grep -E "^\s+-m(arch\|abi)="` |
| `tune` | `-mtune`: под какое ядро оптимизировать | `c++ -v 2>&1 \| grep with-tune` на плате покажет родное ядро. Если стоковый GCC его не знает (ошибка `unknown cpu`), возьмите ближайшее известное. Проверка: `echo 'int main(){}' \| riscv64-linux-gnu-gcc-15 -x c - -mtune=<имя>` |
| `system_libs` | системные библиотеки платы, которые не нужно класть в бандл | на плате: `ldd <ваш бинарник>`; всё, что есть в системе платы (libc, libm, libstdc++...), перечисляется префиксами имён |

### `[toolchain]`: компилятор и инструменты

| Ключ | Что это | Где взять |
|---|---|---|
| `cc`, `cxx`, `readelf` | имена кросс-компиляторов и `readelf` | `apt-cache search riscv64-linux-gnu-gcc`; версия GCC и glibc должны быть совместимы с системой платы (на плате: `ldd --version`, `c++ --version`) |
| `micromamba_url` | откуда качать micromamba | `https://micro.mamba.pm/api/micromamba/linux-64/latest` |
| `conda_channel`, `conda_packages` | канал и пакеты (cmake, ninja, git...) | менять редко |
| `cross_debs` | `.deb`-пакеты кросс-GCC | список зависимостей: `apt-cache depends --recurse --no-recommends --no-suggests --no-conflicts --no-breaks --no-replaces --no-enhances gcc-15-riscv64-linux-gnu g++-15-riscv64-linux-gnu libc6-dev-riscv64-cross libstdc++-15-dev-riscv64-cross \| grep -E "^[a-z0-9]" \| grep -E "riscv64\|cross" \| sort -u` |
| `host_debs` | x86-библиотеки для запуска самого кросс-компилятора | симптом нехватки: `error while loading shared libraries: libisl.so.23`; недостающую библиотеку добавьте сюда |

Пакеты скачиваются `apt download` (root не нужен) и распаковываются `dpkg -x` в `work/toolchain/`.

### `[host]`: требования к серверу (этап `doctor`)

`min_disk_gb` (меньше - ошибка), `comfortable_disk_gb` (меньше - предупреждение), `check_urls` (адреса,
до которых должна быть сеть). Ориентир: сборка OpenVINO заняла 3,1 ГБ.

## `configs/frameworks/<имя>.toml`

### `[source]` и `[[deps]]`: исходники

| Ключ | Что это | Где взять |
|---|---|---|
| `name` | имя папки в `work/src/` | любое, без пробелов |
| `repo` | адрес git-репозитория | страница проекта |
| `version` | тег (или ветка) для `git clone --branch` | `git ls-remote --tags <repo>` |
| `commit` | необязательно: ожидаемый хеш коммита; если тег кто-то сдвинет, `fetch` остановится | тот же вывод `git ls-remote --tags <repo> <тег>` |
| `submodules` | `true`, если нужны подмодули | есть ли файл `.gitmodules` в репозитории |

`[[deps]]` - зависимости с теми же ключами (кроме `submodules`, он необязателен). Они скачиваются вместе
с фреймворком.

### `[[patches]]`: правки исходников

| Ключ | Что это |
|---|---|
| `file` | имя файла в `patches/<фреймворк>/` |
| `dir` | где запускать `git apply`: `.` - корень фреймворка; для подмодуля - его папка (у него свой git) |
| `repo` | необязательно: в каком из скачанных репозиториев (по умолчанию - основной `[source]`) |
| `note` | пояснение, попадает в `MANIFEST.txt` |

Патчи применяются по порядку. Как сделать новый: [ADDING.md](ADDING.md#добавить-патч).

### `[[build]]`: сборка

Блоки выполняются по порядку: сначала зависимости, потом фреймворк.

| Ключ | Что это | Где взять |
|---|---|---|
| `name` | имя (для сообщений и лога `build-<имя>.log`) | любое |
| `system` | система сборки, по умолчанию `cmake` (других пока нет) | |
| `source`, `build_dir` | откуда собирать и где держать сборку | `{src}/...`, `{build}/...` |
| `install_prefix` | необязательно: если задан, после сборки делается `cmake --install` туда | нужен, если следующий блок ищет эту зависимость через `find_package` |
| `targets` | необязательно: собирать только эти цели | список целей: `cmake --build <каталог> --target help` |
| `args` | аргументы `cmake` (`-D...`) | см. ниже |
| `build_type` | необязательно, по умолчанию `Release` | |

Всегда добавляются: `-G Ninja`, `-DCMAKE_TOOLCHAIN_FILE`, `-DCMAKE_BUILD_TYPE`, `-DCMAKE_INSTALL_PREFIX`
(если задан). Остальное - в `args`.

**Откуда брать `args`.** Лучший источник - нативная сборка на самой плате: параметры её конфигурации
лежат в `CMakeCache.txt` (`grep -E "^ENABLE_|^CMAKE_BUILD_TYPE" CMakeCache.txt`) или в истории
команд (`history | grep cmake`). Второй источник - документация фреймворка по сборке. Опции, которые
выключают ненужные части (тесты, Python, GPU), сильно ускоряют сборку.

### `[[bundle]]`: что класть в бандл

| Ключ | Что это |
|---|---|
| `src` | откуда копировать |
| `patterns` | маски имён; `*` захватывает и версионные файлы, и симлинки (`libfoo.so*`). Если маска ничего не нашла, `package` остановится |
| `dest` | подпапка внутри бандла (`bin`, `tbb`...) |

Что нужно кроме самого бенчмарка: все `.so`, которые он загружает. Список: `readelf -d <файл> \| grep NEEDED`
(рекурсивно по библиотекам) или `ldd` на плате, когда нативная сборка работает.

### `[run]`: как запускать на плате (генерирует `run.sh`)

| Ключ | Что это |
|---|---|
| `bench` | путь к исполняемому файлу бенчмарка внутри бандла |
| `library_dirs` | подпапки бандла для `LD_LIBRARY_PATH` |
| `command` | команда запуска; подстановки `{bench}`, `{model}`, `{threads}`, `{niter}`. Перед ней `run.sh` сам ставит `taskset -c 0-(потоки-1)` |
| `metrics` | список `{ name = "...", pattern = '...' }`: какие числа вытащить из вывода в `results.csv` |

`command` проще всего взять из истории нативных запусков на плате (`history | grep benchmark`).

`pattern` - регулярка для `sed -E`; число должно быть в первой группе `(...)`; символ `/` использовать
нельзя. Проверка на готовом логе без запуска бенчмарка:

```bash
sed -nE 's/.*Median:[[:space:]]+([0-9.]+) ms.*/\1/p' threads_8.log
```

Выведет число, если регулярка подходит. Если вывода нет, регулярка не совпала со строкой лога.

### `[verify]`: проверка бандла

| Ключ | Что это |
|---|---|
| `elf` | файлы бандла, которые должны быть ELF под RISC-V и иметь все зависимости |
| `[[verify.contains]]` | `file` и `strings`: строки, которые обязаны быть в бинарнике. Нужны, чтобы доказать, что патч попал в сборку |

Как выбрать строку: имя функции или класса из патча, которое остаётся в бинарнике. Проверка на готовой сборке:
`strings <файл.so> \| grep -c <строка>` либо `riscv64-linux-gnu-nm -C <файл.so> \| grep -ci <имя>`.

## `configs/models/<имя>.toml`

| Ключ | Что это |
|---|---|
| `name` | имя модели |
| `dir` | где лежат файлы модели (от корня репозитория); в git они не хранятся |
| `files` | какие файлы копировать в бандл (в папку `model/`) |
| `entry` | какой из них передавать бенчмарку как `{model}`; должен быть в `files` |
| `format`, `precision`, `input`, `source_hint` | справочные, скриптом не используются |

Для OpenVINO это пара `.xml` + `.bin` (IR). Конвертация моделей в нужный формат в утилиту не входит:
файлы должны быть готовы.
